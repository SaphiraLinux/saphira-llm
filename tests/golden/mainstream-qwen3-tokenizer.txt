# This GGUF declares:
#     tokenizer.ggml.model = gpt2        <-- NOT gpt2 semantics, and NOT unique
#     tokenizer.ggml.pre   = qwen2       <-- the actual pre-tokenizer
#     n_vocab               = 151936     <-- not 50257
#     llama_vocab_type()    = BPE
#
# So a selector that reads model==gpt2 and routes to the GPT-2 backend picks the
# right FAMILY with the wrong PARAMETERS: GPT-2's pre-tokenizer pattern and a
# 50257 vocab, applied to Qwen3 weights. That is a false green: baseline prose
# tokenises correctly, and the failure only appears on spacing, punctuation and
# non-ASCII input. The selector must key on the COMBINATION
# model + pre + vocab size, and must never key on general.architecture alone.
#
# Evidence that the parameters genuinely differ from GPT-2, not just the label:
#   '!' is its own token 1879, and '<' '>' are standalone 314 and 29, so
#   <tag> splits as " <", "tag", ">" -- which is what makes the chat
#   template's angle-bracket control tokens addressable at all.
#   Repeated spaces are preserved as increasing-run tokens 220 " ", 262
#   "   ", so whitespace normalisation is wrong even in the trivial case.
#
# Hard gate: Saphira must produce these ids byte-exactly. Correctness is
# never to be inferred from logits or generated text.
