## THE SELECTOR TRAP, RECORDED BEFORE ANY Saphira TOKENIZER CODE EXISTS
#
# This GGUF declares:
#     tokenizer.ggml.model = gpt2        <-- NOT gpt2 semantics, and NOT unique
#     tokenizer.ggml.pre   = qwen2       <-- the actual pre-tokenizer
#     n_vocab               = 151936     <-- not 50257
#     llama_vocab_type()    = BPE
#
# So a selector that reads model==gpt2 and routes to the GPT-2 backend picks the
# right FAMILY with the wrong PARAMETERS: GPT-2's pre-tokenizer pattern and a
# 50257 vocab, applied to Qwen3 weights. That is a false green: baseline prose
# tokenises correctly, and the failure only appears on spacing, punctuation and
# non-ASCII input. The selector must key on the COMBINATION
# model + pre + vocab size, and must never key on general.architecture alone.
#
# Evidence that the parameters genuinely differ from GPT-2, not just the label:
#   In "Hello, world! (yes) [no] {maybe} <tag>" every bracket and comma is its
#   own token: 11 is ",", 0 is "!", 320 is " (", 314 is " {", 366 is " <" and
#   29 is ">". So <tag> splits into three tokens, which is what makes the chat
#   template's angle-bracket control tokens addressable at all.
#   Repeated spaces are preserved as increasing-run tokens 220 " ", 262
#   "   ", so whitespace normalisation is wrong even in the trivial case.
#
#   CORRECTION, 2026-09-30, after reading the raw vocab bytes. An earlier
#   revision of this file said "1879 is !" and "314 is <". Both were wrong.
#   1879 is " world" and 314 is " {"; the exclamation mark is id 0 and the
#   opening angle bracket is id 366. The conclusion was unaffected -- the
#   punctuation still splits into standalone tokens and the angle brackets are
#   still individually addressable -- but the ids cited as evidence were not.
#   Worth recording that the ids were taken by eye off an aligned list rather
#   than read out of the file, and that reading them is what caught it.
#
# Hard gate: Saphira must produce these ids byte-exactly. Correctness is
# never to be inferred from logits or generated text.

## MACHINE-READABILITY CONTRACT

  text_hex    the exact INPUT BYTES, hex, emitted by the probe from the same
              literal the llama.cpp call receives. The Saphira test rebuilds the
              input from these bytes and NEVER from a retyped string, so the
              expectation cannot drift from what was actually captured.
  ids         token ids exactly as captured from llama.cpp, unchanged.
  decode_hex  the DETOKENIZED OUTPUT BYTES, hex. Compared as bytes, never as a
              UTF-8 string, because these pieces are not individually valid UTF-8
              and a string comparison would silently be a different test.

Per-case field order is: text_hex, the [label] line, ids, pieces, decode_hex.
The empty case has no decode_hex line because it produces no tokens.

This file stays the single source of truth. No test may restate an expected id;
a test carrying its own copy of an expectation is a second source of truth and
it drifts without anyone noticing.
