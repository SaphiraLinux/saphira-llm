# Benchmarks

Every number here is a recorded measurement. Nothing in this file is an
estimate, a projection or a target dressed up as a result. saphira-llm has no
performance numbers yet because it has no kernels yet; when it does, they go
in a separate section below, measured on this same machine, against this same
reference.

### Finding 1 — generation does not scale with cores

Going from 1 to the best measured thread count (22) multiplies generation
throughput by **2.45×** on 22 threads. Prompt processing scales far better
(4.2× from 1 to 14). Per-token decode is dominated by streaming model weights
and the KV cache, not by arithmetic, so there is a large amount of headroom
that no amount of kernel tuning alone will recover.

### Finding 2 — there is a hard cliff between 24 and 28 threads, and it is catastrophic

At 28 threads generation collapses to 1.42 t/s. That is **20× slower than the
22-thread result and 10× slower than single-threaded**. This is not a scheduling
wobble: it is reproducible, it has a low standard deviation, and it is far worse
than having no threading at all.

The best measured configuration, 22 threads, is exactly 8 P-cores × 2 SMT
threads plus 6 E-cores × 1 thread — i.e. all P-core hardware threads plus the
E-cores *without* their SMT siblings. 28 is all 14 cores × 2 SMT, which
includes the E-core SMT siblings. The plausible reading is that the E-core SMT
siblings are being used for decode work they cannot service, but that is a
hypothesis. Phase 2 addresses it with topology-aware placement, and the
placement policy is to be chosen from measurement rather than assumed.

### Finding 3 — `BITNET_X86_TL2` is not a performance question for us

The open question for Phase 0 was whether the T-MAC/LUT kernels (`TL2`) beat the
AVX2 BLAST kernels on this CPU, because `-DBITNET_X86_TL2=OFF` in the shipped
recipe means the installed reference only ever exercises BLAST.

It is settled, for two independent reasons:

1. **`-DBITNET_X86_TL2=ON` does not link at the pinned revision.** The
   `GGML_BITNET_X86_TL2` block of `src/ggml-bitnet-lut.cpp` defines
   `ggml_bitnet_init`, `ggml_bitnet_free`, `ggml_bitnet_can_mul_mat`,
   `ggml_bitnet_mul_mat_get_wsize` and `ggml_bitnet_get_type_bits`, but not
   `ggml_bitnet_mul_mat`, which `ggml.c` calls. The build fails with
   `undefined reference to 'ggml_bitnet_mul_mat'`. This is an upstream defect
   and is the reason the shipped recipe sets the option off.
2. **They are not alternatives anyway.** `GGML_TYPE_I2_S` is type 36 and
   `GGML_TYPE_TL2` is type 42 — distinct GGUF types. `TL2` is reached only when
   a model has been *converted* to it, via `transform_to_tl2()` in
   `utils/convert-hf-to-gguf-bitnet.py`, together with LUT kernels generated by
   `utils/codegen_tl2.py` and block sizes chosen by
   `utils/tune_gemm_config.py`. The official b1.58 GGUF is `I2_S`
   (`LLAMA_FTYPE_MOSTLY_I2_S`, which the converter itself annotates as
   "matches official model"), so the acceptance model can only ever run on the
   BLAST path.

Consequence: **BLAST is the reference ternary path, and it is what Phase 6
optimises.** The T-MAC/LUT idea stays on the record as a possible later
technique to evaluate from first principles, not as something to port.

### Finding 4 — parity must be defined on the raw prompt

`llama-cli` runs in conversation mode and applies a chat template. The same
text fed raw to the reference model produces different tokens:

* `llama-cli` (templated): `The capital of France is Paris. ...`
* raw prompt (see `tests/golden/bitnet2b-capitol.txt`): ` small city, and the capital of France is a small city`

Both are the reference implementation being correct about two different inputs.
The token-parity gate must therefore fix the prompt *and* the tokenisation
(`add_special`), and must compare against the raw-prompt fixtures in
`tests/golden/`. Comparing against a templated CLI session would compare two
different problems.

Also note the CLI's output is only stable when `-st --no-warmup` are used; the
interactive session otherwise carries state that changes the result.

## Golden vectors

Captured with `tools/reference/sllm-logits-ref` at `-t 1`. ggml's reduction
order depends on the thread count, so fixtures are only bit-reproducible at a
fixed thread count; the thread count is recorded inside each manifest.

| Fixture | Tokens | Logit hash (FNV-1a 64) |
| --- | ---: | --- |
| `bitnet2b-capitol` | 6 | `73b3c61d0d59eab5` |
| `bitnet2b-save` | 10 | `625af1c48bfae15e` |

Both were re-captured twice from scratch and were **byte-identical** on every
reproduction, so the fixtures are sound.

### The parity gate, in order of strength

1. **Greedy token sequence identical at temperature 0** on the frozen prompt
   set. This is the product requirement and the hard gate.
2. **Logits agreeing within a tolerance derived from measurement.** saphira-llm
   will use its own reduction order, so bit-exact logit equality is neither
   expected nor the right criterion. The tolerance must be measured, not
   guessed.
3. **The FNV-1a hash** in each manifest is for diagnosing *why* a run differs.
   It is not a pass/fail criterion for saphira-llm.

## Reproducing

```sh
cmake -B build-base -S third_party/BitNet -G Ninja \
  -DCMAKE_BUILD_TYPE=Release -DBITNET_X86_TL2=OFF \
  -DLLAMA_BUILD_TOOLS=ON -DLLAMA_BUILD_UI=OFF -DLLAMA_USE_PREBUILT_UI=OFF \
  -DCMAKE_C_FLAGS="-march=x86-64-v3 -O2" \
  -DCMAKE_CXX_FLAGS="-march=x86-64-v3 -O2"
cmake --build build-base --target llama-bench llama-cli -j

./build-base/bin/llama-bench \
  -m /var/lib/spoon/models/ggml-model-i2_s.gguf \
  -t 1,4,14,28 -p 512 -n 128 -r 3 -o json
```

The build here is verified to reproduce the installed `/usr/bin/llama-cli`
token-for-token; the only difference in output is the build banner string,
because the recipe's only source patches touch `build-info.cpp.in` and the
Python helper entry points.
